Overview

Automated Ken watches your snaps' channels and upstream projects, opens version-bump PRs, tests new versions on real amd64 and arm64 machines, reviews the screenshots with a local vision model, and promotes each version to stable for all its architectures at once.

📦
Channel tracking

stable, candidate, beta and edge per architecture, plus open issues and PRs.

🔧
Version bumps

New upstream releases become PRs on your packaging repos, opened by a bot account.

🖥
Real-hardware testing

Each architecture is tested on its own runner machine, in a real desktop session.

🚀
Release sets

amd64 and arm64 are promoted to stable together, after every architecture passes.

First login & onboarding

Sign in with GitHub. The first account to sign in becomes the administrator; everyone after that must be added to the allowlist on the Admin page first.

The onboarding wizard asks for:

  1. Snap Store publisher — your Store account name (e.g. ken-vandine). Every snap it publishes is added automatically.
  2. GitHub token — optional in the wizard, but most features need it (see below).

When you finish, the first data collection runs in the background and your agents are scheduled. Everything can be changed later in Settings.

Dashboard overview

The dashboard lists every tracked snap with its channel versions. Attention Needed at the top highlights snaps with a newer version in candidate or edge than in stable.

Channel version badges

  • green — same as stable (or is stable)
  • amber — differs from stable
  • — — not published in this channel
  • — — not published in stable at all

Refreshing

Channel maps and issues refresh on the collection interval (Settings → Publisher, default 6 hours). Refresh All runs a collection now; a snap's detail page has its own Refresh.

The snap detail page shows the full channel map — every channel and architecture with its version and revision.

Adding snaps

Snaps published by your Store account are discovered automatically on the first collection. Use Add Snap to track any other snap by name.

Each snap has two repository URLs, filled in from Store metadata (or by finding a snapcraft.yaml with that name in your GitHub repos) and editable on its detail page:

  • Packaging repo — where the snapcraft recipe lives. Needed for version bumps and rebuilds.
  • Upstream repo — the upstream project, for issues/PRs and upstream maintenance.

Issues & Pull Requests

Open issues and PRs from each snap's packaging and upstream repos (GitHub or GitLab) are shown on its detail page, with tabs to filter by type and by repo, and counted on the dashboard.

How testing works

Every test job is one snap version on one architecture, run on an enrolled runner of that architecture:

  1. The runner installs the snap from the job's channel (candidate or edge) in its real desktop session.
  2. It launches the app, lets it render, and takes a screenshot (a smoke test). Snaps marked as a console app on their detail page are launched inside a terminal window instead of bare, since a text UI has nothing to screenshot when run headless.
  3. The screenshot and the log are uploaded; the run is passed if the app stayed running and the screenshot isn't blank.
  4. Candidate runs are then reviewed by the vision model (see Results & AI review).

Architectures

Only amd64 and arm64 are tested. A version built for both is one row on the Testing page and one release set; architectures a snap also ships (armhf, riscv64, …) are ignored because there's no runner for them.

Candidate vs edge

  • Candidate — the promotion path. Passed runs are reviewed, and the release set can be promoted to stable.
  • Edge — test-only. Version-bump PRs are tested from edge; there's no promotion from edge.

Runners

A runner is a dedicated desktop or laptop running the automated-ken-runner snap. It polls this server for work over HTTP(S) — no inbound ports — and only takes jobs:

  • for its own architecture (reported automatically),
  • belonging to the user it's enrolled under,
  • while its desktop has been idle for 2 minutes and isn't locked, so it never disturbs someone using it.

Enroll at least one amd64 and one arm64 runner. A job for an architecture with no runner waits in the queue.

Setting one up

sudo snap install automated-ken-runner --classic
echo "$USER ALL=(root) NOPASSWD: /usr/bin/snap" | sudo tee /etc/sudoers.d/automated-ken-runner
automated-ken-runner prepare-machine      # screenshot extension, autologin, no screen lock

# On the Runners page: "+ Enroll a runner", then run the command it shows:
automated-ken-runner enroll --server http://<this-host>:9080 --token <token>
systemctl --user enable --now snap.automated-ken-runner.run.service
Use a dedicated machine. prepare-machine enables autologin and disables the screen lock, so anyone with physical access has full access to whatever is logged in. The runner needs Ubuntu with GNOME, logged into a graphical session. The server must be reachable from the runner — set snap set automated-ken bind=0.0.0.0.

Runner status

  • idle — ready for a job
  • busy — running a job, or someone is using the machine
  • locked — screen locked; won't take jobs
  • offline — no heartbeat for 90 seconds

The queue

The Runners page lists queued and running jobs with their architecture. Use ▲/▼ to change priority and Cancel to drop a queued job or stop a running one (the runner stops the test within about 15 seconds). A job running longer than the runner job timeout (Settings → Testing, default 10 minutes, counted from when a runner picks it up) is marked failed and its runner freed.

Console apps

Every snap gets the same generic smoke test: install, launch, let it render, screenshot, done — no per-repo test code to write or maintain. There's no per-repo Robot/YARF suite support; a suite would run against yarf's Mir or Vnc platform, and neither has a working way to drive input/capture on a real GNOME/Wayland session (yarf's Mir platform needs wlroots-only Wayland protocols Mutter doesn't implement, and its Vnc platform has no local server to talk to on a stock GNOME desktop).

If a snap's UI is text/terminal only, launching it bare leaves nothing on screen to screenshot. Check Console app on the snap's detail page and the runner launches it inside a terminal window (xterm) instead, then screenshots that.

Running tests

The Testing page's Needs testing list shows every snap whose candidate or edge version differs from stable — one row per version with all its architectures. Run Tests (amd64, arm64) queues one job per architecture; each row shows every architecture's latest run.

Statuses: pending (queued) → triggered (claimed by a runner) → running → passed / failed. Candidate runs then go through reviewing. A failed run's page has a log link with everything the runner captured.

Automatic testing

With Enable automatic testing (Settings → Testing), every collection queues tests for any candidate or edge version and architecture that hasn't been tested yet. Version-bump PRs are always tested, regardless of this setting. This includes new revisions from a manual Rebuild All Snaps Now or the Stale Build Scanner — publishing itself doesn't queue a test, but the next scheduled collection (or a manual "Refresh Now") will notice the new candidate/edge revision and queue one if this setting is on.

Results & AI review

Open a run from the Testing or Runners page to see its screenshots, log, review, and the other architectures in its release set.

When a candidate run passes, the local vision model compares its screenshots with the last stable screenshots for the same architecture. The first time a snap is tested there's no baseline, so it only checks that the app visibly launched, and keeps the confidence low. The verdict is approve, reject or needs review, with a confidence score. When a release set is promoted, its screenshots become the new stable baseline for each architecture.

Without a vision model available, the review is skipped and the run needs a manual decision — nothing is auto-approved.

Promoting a release set

A candidate version is promoted to stable for all its architectures at once, so stable never ends up with amd64 on the new version and arm64 on the old one.

  • Pending Promotion (Testing page) and each run's page show the release set and every architecture's state.
  • When every architecture has passed, 🚀 Promote set to Stable releases all of their revisions.
  • If any architecture hasn't passed — not tested, still running, failed — the button becomes ⚠ Promote (override).

Overriding a missing architecture

An override promotes only the architectures that passed. It's deliberately hard to do by accident:

  1. The confirmation dialog names every architecture that will be left out.
  2. The server refuses a partial promotion unless that confirmation was given.
  3. Each promoted run records which architectures were skipped; a version-bump PR promoted this way is marked partially promoted.

Auto-promote

With Auto-promote on (Settings → Agents & AI), a release set — including one produced by a merged version bump — is promoted automatically once every architecture has passed and been approved at or above the confidence threshold. If any architecture is missing or not approved, nothing is auto-promoted — use the override if you mean to release without it.

Version-bump PRs

When the Release Scanner finds a newer upstream release for a part in a snap's snapcraft.yaml, the Version Bumper opens a PR updating it (one open bump per part at a time). The PR Monitor then:

  1. waits for the PR's CI to pass — if it fails and auto-fix CI is on, a fix is delegated to the coding backend, and a later green run is picked up;
  2. queues one test per architecture from edge;
  3. has each architecture's screenshots reviewed, and gives the PR one verdict — a regression on any architecture rejects the set;
  4. merges it if Auto-merge is on and the verdict is approve.

Those edge tests only gate the merge — they don't test the revisions that would ship. With Auto-promote on, a merged bump carries on to stable:

  1. Waiting for candidate release — when CI has published the new version for every architecture it's in candidate; if CI only published it to edge, those revisions are released to candidate together.
  2. Testing candidate — one test per architecture of the exact candidate revisions, reviewed like any candidate run.
  3. Stable — once every architecture is approved, the set is promoted. If any fails or isn't approved, the bump stops at needs review with the reason.

With auto-promote off, a merged bump stops at merged, and its page shows the candidate release set to promote by hand.

On Version Bumps, open a PR to see each architecture's pre-merge status and screenshots side by side, then Merge, Reject or Re-run Tests (re-tests every architecture; only the newest run per architecture counts). After merge it shows the candidate release set with Promote (all architectures, or a confirmed override) and Re-run candidate tests. PRs merged or closed on GitHub are picked up automatically, and a merged bump never blocks the next bump for the same part.

Delegated coding tasks

Work that needs real code changes is delegated to the coding backend (Settings → Agents & AI; GitHub Copilot cloud agent by default), which opens PRs for you to review. All are opt-in:

  • Auto-fix failing CI on version-bump PRs.
  • Auto-maintain upstream repos you own — dependency updates, review requests on your open PRs, and fixes for a few issues per run.
  • Fleet normalization — a one-off pass (run from Settings) opening a PR per packaging repo to drop legacy sync-release-style workflows, normalise the build/publish workflow and add an AGENTS.md.

Every dispatched task and its PR is listed on Coding Tasks.

Local AI (Lemonade)

A private Lemonade server is bundled and started automatically — no setup. It's used for screenshot review (a vision model) and drafting PR descriptions, and downloads its models the first time each is needed. The Agents page header shows whether it's connected; Test Connection checks it.

To use a Lemonade server you already run, choose System Lemonade in Settings → Agents & AI and enter its URL (and API key, if it needs one). Model override replaces the default model for every task.

Admin & allowlist

The Admin page (admins only) lists registered users and the access allowlist. Only GitHub accounts on the allowlist can sign in; usernames are matched case-insensitively. Admins can grant or remove admin rights for other users, but not themselves.

Every user has their own snaps, runners, tests, settings and agent activity.

Troubleshooting

Jobs stay "pending"

  • Check the Runners page has an idle runner of the job's architecture, enrolled under your account.
  • A runner only takes jobs after 2 minutes of desktop inactivity, and never while locked. Run automated-ken-runner status on it.
  • A runner showing the wrong or no architecture corrects itself on its next heartbeat after an upgrade.

Runner shows "offline"

On the runner: systemctl --user status snap.automated-ken-runner.run.service and journalctl --user -u snap.automated-ken-runner.run.service -f. Check it can reach this server's address and port.

Jobs fail at "snap install"

The runner needs passwordless sudo for snap; automated-ken-runner prepare-machine checks for it and prints the sudoers line to add.

Runs pass but have no screenshots, or fail as blank

Screenshots come from a GNOME Shell extension that prepare-machine installs; it only loads after a fresh login, which is why prepare-machine reboots. The screen must not be blanked — re-run prepare-machine if power settings were changed.

A release set isn't auto-promoted

Every tested architecture must have passed and been approved at or above the threshold. The run page's release-set card and the run note say what it's waiting on. Use ⚠ Promote (override) to release without a missing architecture.

No version-bump PRs are opened

Set the bot account token in Settings → Agents & AI, and make sure the snap has a GitHub packaging repo whose snapcraft.yaml part uses a source-tag (commit-pinned parts can't be bumped). Only one open bump per part is allowed at a time.

Promotion fails

Check the Store credential in Settings is current (snapcraft export-login -) and can release the snap. The error is shown on the run page.

GitHub rate limits

Set a GitHub token — the limit goes from 60 to 5,000 requests an hour.

Reproducing a smoke test by hand

sudo snap install mysnap --channel candidate
snap run mysnap          # or: xterm -e snap run mysnap, for a console app
